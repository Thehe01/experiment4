Act as an expert in cybersecurity threat intelligence annotation.
From the provided text, extract named entities using EXCLUSIVELY the four categories defined below. You will also extract relations between these entities when explicitly supported by the text (see Relation Extraction section).

ENTITY TYPES AND RULES

- Vulnerability: a literal CVE identifier as explicitly written in the text. This includes the standard format CVE-YYYY-NNNN (e.g., CVE-2021-44228) as well as variant mentions with minor formatting deviations that are explicitly present in the input, such as "CVE- 2016-5195" (with a space after the hyphen) or "CVE 2024-36401" (with a space instead of hyphen). Known vulnerability names (like "Log4Shell", "Snake", "EternalBlue") or non-CVE descriptions must NOT be labeled as Vulnerabilities, even if they denote a known flaw. Extract the exact verbatim substring from the text as the entity text (including any spaces or deviations). Set normalized_id to the canonical CVE-YYYY-NNNN form (e.g., "CVE-2016-5195", "CVE-2024-36401") by removing extraneous spaces; if the text uses "CVE 2024-36401", normalized_id is "CVE-2024-36401". Only exact CVE substrings (with or without minor whitespace deviations) are valid. Every distinct explicit mention of a CVE substring in the text (even if the same canonical ID appears multiple times) must be extracted as a separate entity with its own verbatim span and offsets (exhaustive explicit identifier mention policy).

- Weakness: a specific CWE identifier (e.g., CWE-89) OR a fundamental flaw class explicitly described in the text as a vulnerability type (e.g., "server-side request forgery", "path traversal", "improper authentication"). If a CWE-xxx token appears, extract it as Weakness and set normalized_id to that CWE-xxx; if only a flaw class name appears without a CWE token, extract the exact phrase as Weakness and set normalized_id to the corresponding CWE if widely known or null if unspecified.

- Configuration: a specific product, software, component, device, or CPE identifier that is EXPLICITLY stated in the text as affected by, targeted by, or subject to a vulnerability or attack technique (e.g., "in Microsoft Exchange Server" within a sentence describing CVE-2021-26855, or a CPE-like string). A product/component name is extracted as Configuration ONLY if the text directly presents it as an affected/targeted item (e.g., "vulnerability in X", "X affected by", "attackers used TXXXX against X", "flaw in X") OR it appears as a clear CPE-style identifier. The following are EXCLUDED and must NOT be tagged as Configuration under any circumstances:
  * Generic filenames, IP addresses, ports, or arbitrary strings not clearly identifiable as products/components (e.g., "comadmin.dat", "104.155.149[.]103", "443", "winds.exe").
  * Vendor names alone mentioned in passing (e.g., "Webroot" stated without context of being affected/targeted).
  * Cloud services or product names mentioned incidentally without explicit affected/targeted context (e.g., "Microsoft OneDrive" referenced only as a data storage location, not as a compromised component).
  * Any product/component not explicitly linked to a vulnerability or technique in the text.

  IMPORTANT CONFIGURATION EXTRACTION RULES:
  * Every distinct verbatim affected/targeted product or component phrase in the text must be extracted as a SEPARATE Configuration entity, even if it is an abbreviated vs full name variant referring to the same product (e.g., both "SimpleHelp" and "SimpleHelp RMM" must be separately extracted if both appear explicitly as affected/targeted). Do not merge or skip variant mentions.
  * For normalized_id, use the official NVD CPE 2.3 vendor/product formatting. Use the canonical NVD vendor field (e.g., for SimpleHelp the NVD vendor is "simple-help" with hyphen, not "simplehelp"; for ManageEngine the vendor is "zohocorp"). If unsure of exact NVD vendor, use the most formal vendor string inferred from the text but prefer hyphenated official forms where known. Provide cpe:2.3:a:vendor:product:*:*:*:*:*:*:*:* as the normalized_id pattern.
  * Example: "SimpleHelp" -> normalized_id "cpe:2.3:a:simple-help:simplehelp:*:*:*:*:*:*:*:*"; "SimpleHelp RMM" -> normalized_id "cpe:2.3:a:simple-help:simplehelp:*:*:*:*:*:*:*:*".

- AttackTechnique: a MITRE ATT&CK technique ID in the form T#### (e.g., T1190, T1090.002, T1055.001) or explicitly named attack method. Each distinct ID occurrence must be its own entity containing only the exact ID substring (e.g., from "Valid Accounts (T1078)" extract "T1078" only). Both sub-technique IDs (e.g., T1090.002) and parent technique IDs (e.g., T1090) are valid when explicitly stated. IDs may appear with brackets (e.g., "[T1055.001]") or newline-separated (e.g., "T1059.001\n") – extract only the exact T-code token without brackets or whitespace. If a technique ID is split by whitespace in the text (e.g., "T1566.0 01"), extract the exact verbatim split substring as text (e.g., "T1566.0 01") and set normalized_id to the canonical joined form ("T1566.001"). IMPORTANT: MITRE ATT&CK tactic IDs (TA####, e.g., TA0011, TA0008, TA0007, TA0005, TA0006) are NOT in evaluation scope and must NEVER be extracted as AttackTechnique or any other type. Only T-code technique IDs qualify. Do NOT tag software/tool IDs such as S0508, S1063, S1054 as AttackTechnique.

RELATION EXTRACTION (optional but required when explicit in text)
When the text explicitly links a Vulnerability to a Configuration (affected/targeted) or a Vulnerability to an AttackTechnique (exploited via), extract a relation with:
- source: id of the source entity (e.g., Vulnerability)
- target: id of the target entity (e.g., Configuration or AttackTechnique)
- type: "affects" | "exploited_by" | "targets"
- evidence_start: start offset of the supporting phrase
- evidence_end: end offset (exclusive) of the supporting phrase
Only output relations that are explicitly grounded in the text.

RULES
1. All entity text MUST be an exact verbatim substring from the input text (including any spaces in CVE mentions such as "CVE- 2016-5195" and split technique IDs such as "T1566.0 01").
2. Provide 0-based start and end character offsets based on the input text. end is exclusive, so text[start:end] equals the entity text exactly.
3. For normalized_id, provide the canonical identifier if present (e.g., standard CVE ID without extra spaces, CWE-xxx, canonical CPE 2.3 URI for products explicitly affected/targeted per NVD vendor rules, or T-code for ATT&CK); otherwise null.
4. Do not output repeated duplicate entries for the identical mention span (same start/end). But DO extract every distinct explicit mention of the same canonical entity as separate entries (exhaustive explicit identifier mention).
5. Extract only entities that satisfy the strict definitions. Skip any span that does not clearly fit one of the four types per the rules.
6. For AttackTechnique, capture solely the exact T-code token (including internal whitespace if present in source) as entity text; never the surrounding descriptive words, brackets, or TA-codes.
7. Never infer or insert entities not present as exact substrings in the input text. Do not hallucinate configurations, products, vulnerability names, or technique IDs that are not explicitly written in the provided text.
8. Output ONLY the specified JSON schema fields per entity: id, text, type, start, end, normalized_id. Do not add fields beyond the specified schema (e.g., no "evidence", "notes", or other extra keys). Relations use: source, target, type, evidence_start, evidence_end.
9. TA#### codes (MITRE ATT&CK tactics) are explicitly out of scope and must not appear in the output under any type.
